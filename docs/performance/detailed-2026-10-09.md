# Detailed statistics follow-up, October 9, 2026

The user reported an 18-second load. The running dev binary was `target/debug/time-tracker.exe`, with unoptimized Rust code. The installed 1.11.8 support profile recorded a 258-day Detailed query taking 5,638 ms in the backend and 5,825 ms including IPC, returning 29,487 apps and 46,602 distinct titles. Browser work scaled with every eligible app row, and each row mounted an `AppTitleDetails` query observer even while its dialog was closed. The number of eligible rows depends on the tab and duration filter: the fresh dev snapshot has 98 in Daily Avg and 6,748 in Total.

## Changes

- The app sidebar renders its viewport plus four rows of overscan on either side. All entries remain reachable through normal scrolling, with original ranking, click/context actions, title dialogs and duration bars. A 30,000-row test verifies fewer than 25 mounted rows and working actions on both the first and final entry. The header stays visible while the list scrolls.
- Long Detailed queries read the union of overlapping current/previous ranges once. Previous-period filtering is captured before current-device filtering, preserving existing behavior. Device/manual-time combinations and full serialized output are compared directly with the old two-read behavior.
- `npm start` now selects the optimized `performance` Cargo profile, which retains debug assertions and every dev isolation guard. `scripts/start-dev.mjs` forwards Tauri flags before the Cargo separator correctly on Windows. For profiling without native watching: `npm.cmd start -- --no-watch`.
- The benchmark uses one frozen timestamp for both implementations. Previously, advancing wall time could change previous-period clipping even on an immutable database. Failure diagnostics now report changed field names instead of dumping private app-title histories.
- The opt-in native scenario records mounted rows and active title-query observers. It records whether paint was observed; hidden samples are data/DOM-readiness measurements, never visible screen timings.

## Measured database result

The full 260-day query, same isolated snapshot and optimized profile, three repetitions:

| | Before | After |
| --- | ---: | ---: |
| Mean backend time | 2,666 ms | 2,213 ms |

Time reduction: **16.98%** for the additional shared-read optimization. This comparison isolates the database change; it does not include the sidebar or dev-profile improvement. The broader frozen-legacy suite also passes with the new implementation.

Validation: 32 Rust checks passed in the broad run, plus the focused full-history reuse benchmark. 40 frontend tests and the production frontend build passed. Raw evidence: [detailed-2026-10-09.json](detailed-2026-10-09.json).

## Native dev screen measurements

The optimized native dev application ran on a fresh read-only production snapshot. Relevant query caches were cleared before every Detailed open. Two sets of three runs, all with visible paint observed:

| Area | Runs | Mean | Range |
| --- | ---: | ---: | ---: |
| Uncached full-history Detailed | 6 | **3,522 ms** | 3,043–4,537 ms |
| Trend open | 6 | 1,926 ms | 1,345–2,586 ms |
| Cached switch to Total | 3 | **73 ms** | 70–76 ms |

Both Daily Avg and Total mount only 24 rows and 24 title-query observers. Total retains all 6,748 eligible apps in the scroll range. All three native SVG gap checks passed (four paths, six finite segments). Initial Detailed render/paint telemetry attributed roughly 45–75 ms to commit and paint, with the remaining load primarily waiting for data. The 18-second report and the production support profile are contextual evidence; they are not a matched end-to-end before/after benchmark. These native results do not claim a production deployment.

The installed application and its production data were only inspected read-only. All test writes and native interactions use `time-tracker-dev/apptest.db`. No installer, production restart, sync, updater or Google Calendar network operation was performed.
